# Distributed Systems: Consensus, Replication, CRDTs, Sharding, and CAP

Prerequisite: §16 (a single node's transaction/consistency machinery -- this file is about coordinating *many* nodes, each potentially running something like §16 internally, in the presence of failures and network partitions).

## Why Consensus Is Needed At All

A single database node can just... decide things, in program order, with no ambiguity. The moment you replicate data across multiple nodes for fault tolerance, you need those nodes to *agree* on things (what the current leader is, what order operations happened in, whether a given write actually committed) despite nodes crashing, restarting, and messages being delayed, dropped, or reordered by the network. **Consensus** is the formal problem of getting a set of nodes to agree on a single value (or a single ordered sequence of values, for the more practically useful "replicated log" framing) even when some nodes fail, without ever agreeing on two *different* values (safety) and while still eventually agreeing on *something* as long as enough nodes are up and can communicate (liveness).

## Raft

Designed explicitly to be easier to understand and implement correctly than Paxos (below), by decomposing consensus into three largely-separable subproblems:

**Leader election**: at any time, nodes are in one of three states -- Follower, Candidate, or Leader. Each node has a randomized **election timeout**; a Follower that doesn't hear from a Leader within that timeout becomes a Candidate, increments a monotonic **term** number, votes for itself, and requests votes from every other node. A Candidate that receives votes from a majority becomes Leader for that term. The **randomized** timeout is a deliberate mechanism to avoid a tie: if every node's timeout were identical, every node could become a Candidate simultaneously, split the vote indefinitely, and never converge -- randomization makes exactly one node's timeout fire first, in the common case, letting it win before others even start an election.

**Log replication**: once elected, the Leader is the *only* node that accepts client writes -- it appends the write to its own log and replicates it to Followers; an entry is considered **committed** once a majority of nodes have it in their log, at which point it's safe to apply to the actual state machine (execute the write) and acknowledge the client.

**Safety properties** Raft guarantees by construction: **Election Safety** (at most one leader per term -- guaranteed by requiring a strict majority of votes, so two candidates in the same term can't both win); **Leader Append-Only** (a leader never overwrites or deletes entries in its own log, only appends); **Log Matching** (if two logs contain an entry with the same index and term, every preceding entry in both logs is identical -- enforced by the replication protocol checking a "previous entry matches" condition before accepting a new append); **Leader Completeness** (a leader for a given term contains every entry committed in any earlier term -- guaranteed by only allowing nodes whose log is at least as up-to-date as a majority to win an election); **State Machine Safety** (if a node has applied a given log entry to its state machine, no other node will ever apply a *different* entry for that same log index -- following directly from Log Matching plus only applying entries once they're committed).

## Paxos

The original consensus algorithm (Lamport, late 1980s), solving the same problem via a two-phase protocol: **Prepare/Promise** (a proposer picks a proposal number and asks acceptors to promise not to accept any *lower*-numbered proposal, learning about any proposal an acceptor may have already accepted) followed by **Accept/Accepted** (the proposer, having learned of any prior accepted value, either proposes that same value or its own if none existed, and acceptors accept it unless they've since promised a higher-numbered proposal to someone else). Basic Paxos, as originally described, agrees on a *single* value per full run of the protocol -- practical systems need a continuous, ordered log of values (a replicated log, matching what Raft directly targets), which requires **Multi-Paxos**: running many Paxos instances, one per log slot, with an optimization that elects a stable leader (skipping the Prepare phase on subsequent instances once one proposer is established as the de facto leader) to avoid paying the full two-phase cost for every single log entry. Paxos is widely regarded as *correct* but notoriously difficult to reason about and implement correctly in its full, practical (Multi-Paxos plus the many real-world edge cases the original papers underspecify) form -- which is the specific, explicit motivation Raft's designers cited for creating an alternative with the identical safety guarantees but a deliberately more decomposable, implementable specification.

## Vector Clocks

A mechanism for tracking **causality** (did event A happen-before event B, or are they concurrent/unrelated) across nodes without a shared, synchronized clock: each node maintains a vector of counters, one per node in the system, incrementing its own entry on each local event and merging (taking the elementwise maximum) whenever it receives a message carrying another node's vector. Two vector clocks can be compared: if every entry in A is ≤ the corresponding entry in B (and at least one is strictly less), A happened-before B; if neither dominates the other, the events are **concurrent** (genuinely unordered with respect to each other -- neither caused the other, which is a real, first-class possibility in a distributed system, not just missing information). This is strictly more informative than a simple **Lamport timestamp** (a single incrementing counter per node, also updated via message-passing) -- Lamport timestamps give a total order sufficient to detect *some* happens-before relationships, but two events with different Lamport timestamps aren't guaranteed to actually be causally related; vector clocks can definitively distinguish "A caused B" from "A and B are concurrent," which Lamport timestamps alone cannot.

## CRDTs (Conflict-Free Replicated Data Types)

Data structures specifically designed so that **any two replicas, having received the same set of updates in any order, converge to the same state** -- eliminating the need for a consensus round on every single update, at the cost of restricting what operations/merge semantics are expressible. **State-based CRDTs** replicate by periodically sending a replica's *entire current state* to others, merged via a mathematically commutative, associative, and idempotent merge function; **operation-based CRDTs** instead broadcast individual operations, which must themselves be designed to commute (applying them in any order produces the same result). Canonical examples: a **G-Counter** (grow-only counter) keeps a per-node counter vector and merges via elementwise max, with the total being the sum -- concurrent increments from different nodes never conflict because they're tracked in separate vector slots; a **PN-Counter** extends this with a second G-Counter for decrements, giving a counter that supports both increment and decrement without conflicts; an **OR-Set** (Observed-Remove Set) tags each added element with a unique identifier, and a removal only removes the specific *observed* tagged instances, correctly handling the case where one replica concurrently re-adds an element another replica is removing (a plain "last write wins" set would lose that add or produce different results on different replicas, violating the convergence guarantee). CRDTs are the mechanism behind systems that need to accept writes on multiple replicas *simultaneously*, even while partitioned from each other, and still guarantee they'll agree once connectivity is restored -- collaborative editing systems and some multi-region databases use exactly this family of technique.

## Replication

**Synchronous replication** waits for one or more replicas to acknowledge a write before confirming it to the client -- stronger durability/consistency guarantee, real added latency (bounded by the slowest required replica). **Asynchronous replication** confirms immediately and propagates in the background -- lower latency, but a leader failure before propagation completes means acknowledged writes can be lost. **Quorum reads/writes** (the `R + W > N` formulation, where `N` is the total replica count, `W` the number of replicas a write must reach before being acknowledged, and `R` the number a read must consult) guarantee that any read quorum and any write quorum necessarily overlap in at least one replica -- so a read is guaranteed to see the most recent acknowledged write, without every single replica needing to be synchronously updated on every write, a tunable middle ground between full synchronous replication (`W = N`) and no consistency guarantee at all (`W = 1`, `R = 1`).

## Sharding and Partitioning

**Range partitioning** assigns contiguous key ranges to different shards -- efficient for range queries (a query for keys A-C touches only the shards covering that range) but prone to **hotspotting** if writes cluster around a narrow key range (a monotonically increasing key like a timestamp or auto-increment ID concentrates all recent writes onto whichever shard currently owns the "newest" range). **Hash partitioning** distributes keys via a hash function instead, spreading load much more evenly at the cost of making range queries expensive (a range query now has to fan out to every shard, since consecutive keys are scattered arbitrarily). **Consistent hashing** solves the specific problem of "adding or removing a shard shouldn't require remapping most existing keys" -- nodes and keys are both hashed onto the same conceptual ring, and a key is owned by the next node clockwise from its hash position; adding/removing one node only reassigns the keys between it and its immediate neighbor on the ring, not the entire keyspace, which is what makes elastic scaling (adding capacity without a full data reshuffle) practical.

## Leader Election (Outside of Consensus Protocols)

Simpler algorithms exist for systems that just need *a* coordinator, without the full replicated-log guarantees Raft/Paxos provide: the **Bully algorithm** (a node detecting the current leader is down announces an election; any higher-ID node that's alive "bullies" its way in and takes over the election, so the highest-ID live node always eventually wins) and **ring-based election** (nodes arranged in a logical ring pass an election message around; the highest ID seen by the time the message returns to its originator wins) are both simpler, weaker-guarantee alternatives -- adequate for coordinating some auxiliary role (which node runs a periodic job) but not a substitute for consensus when the actual *data* needs replicated, agreed-upon ordering.

## Distributed Transactions

**Two-Phase Commit (2PC)**: a coordinator asks every participant to **prepare** (do all the work, durably log it, and vote yes/no, but don't yet make it visible/final) and only **commits** once *every* participant has voted yes; if any participant votes no (or times out), the coordinator tells everyone to **abort** instead. The well-known weakness: if the coordinator crashes *after* participants have voted yes but *before* sending the final commit/abort decision, those participants are **blocked**, holding their prepared-but-undecided state (and any locks it implies) indefinitely until the coordinator recovers -- 2PC has no way for participants to resolve this among themselves. **Three-Phase Commit (3PC)** adds an extra phase specifically to bound this blocking window (participants can time out and safely resolve the outcome themselves in more scenarios) but at real added latency cost and with its own remaining edge cases under network partitions, which is part of why it's less commonly deployed in practice than the conceptually simpler 2PC combined with other mitigations. The **Saga pattern** sidesteps distributed atomicity entirely: instead of one all-or-nothing transaction spanning multiple services, a saga is a sequence of local transactions, each with a defined **compensating action** that semantically undoes it -- if a later step fails, previously completed steps are undone by running their compensations in reverse, trading strict atomicity for avoiding 2PC's blocking/coordination overhead, at the cost of the compensations needing to be carefully designed (and the intermediate, partially-completed state being genuinely, if transiently, visible to the rest of the system).

## CAP Theorem

The precise statement: in the presence of a **network partition**, a distributed system must choose between **Consistency** (every read sees the most recent write, or an error) and **Availability** (every request receives a non-error response, though possibly not reflecting the most recent write) -- it cannot guarantee both simultaneously *during* the partition. The commonly-missed nuance: partition tolerance isn't really an optional third choice in any real distributed system spanning more than one machine -- networks *will* partition eventually, so CAP in practice reduces to "when a partition happens, do you choose C or A" (CP systems refuse requests/return errors on the minority side of a partition to preserve consistency; AP systems keep serving requests on both sides, accepting that they may diverge and need reconciliation later, as CRDTs above are one principled way to handle). The **PACELC** extension makes the *other* half of the tradeoff explicit, which CAP alone doesn't address: **even absent a partition** (the "Else" in PACELC), a system still has to choose between **Latency** and **Consistency** -- serving a read from the nearest replica immediately (lower latency, possibly stale) versus waiting to confirm it reflects the latest write (higher latency, guaranteed current) -- a real, everyday design tension CAP's partition-focused framing doesn't capture on its own.

## Key Takeaways

- Raft's three subproblems (leader election, log replication, safety) are the same problem Paxos solves, deliberately decomposed for implementability -- both provide equivalent guarantees, but Raft was explicitly designed to be easier to get right.
- Vector clocks capture genuine concurrency (neither event caused the other) that a single Lamport timestamp cannot distinguish from "unknown ordering" -- this distinction is exactly what CRDTs' merge functions need to handle correctly.
- CAP's real-world content is "choose C or A during a partition," not "pick any two of three" -- partition tolerance isn't optional for any system spanning more than one node, and PACELC captures the equally real latency/consistency tradeoff that persists even when nothing is partitioned.

## Interview Notes

- "Why does Raft use a randomized election timeout instead of a fixed one?" -- a fixed timeout risks every follower becoming a candidate simultaneously, splitting the vote repeatedly with no convergence; randomization makes one node's timeout fire first in the common case, letting it win the election before others even begin.
- "What's the core weakness of Two-Phase Commit, and how does the Saga pattern avoid it?" -- 2PC can leave participants blocked indefinitely if the coordinator crashes after they've voted yes but before the final decision arrives; Sagas avoid this by never requiring cross-service atomicity in the first place, instead running independent local transactions with compensating actions to undo completed steps if a later step fails.
