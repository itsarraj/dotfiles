# Storage Engines: mmap, Page Cache, B-Trees, LSM-Trees, WAL, and SSD/NVMe Internals

Prerequisite: handbook §1.8 (paging/page faults), §36.5 (copy-on-write). This file covers how storage engines (databases, key-value stores) actually use the OS's I/O primitives, and the two dominant on-disk data structure families.

## mmap

`mmap`ing a file maps it directly into the process's virtual address space -- reads and writes become ordinary memory accesses, with the kernel transparently faulting pages in from disk (handbook §1.8's page-fault mechanism, exactly as it works for any other lazily-populated mapping) rather than requiring explicit `read`/`write` syscalls per access. This gives a genuinely convenient programming model (treat a multi-gigabyte file as if it were an in-memory array) but hands *all* caching/eviction decisions to the kernel's general-purpose page cache (below) -- which is exactly the tradeoff many databases deliberately opt out of via direct I/O, since a database usually has better information than the kernel's generic LRU-ish policy about which pages are actually hot (e.g., "this B-tree's root and top few levels should basically never be evicted").

## Direct I/O (O_DIRECT)

Opening a file with `O_DIRECT` bypasses the page cache entirely -- every read/write goes straight to the storage device, with the *application* responsible for its own buffering/caching strategy instead of relying on the kernel's. Databases commonly want this specifically to avoid **double buffering**: without it, data lives both in the database's own buffer pool (handbook-style, application-managed cache, §16's database-internals material) *and* redundantly in the kernel's page cache, wasting memory holding two copies of the same hot pages and adding an extra memory-to-memory copy on every read that the database's own cache could have served directly. The real cost: `O_DIRECT` I/O typically has stricter alignment requirements (buffer address, file offset, and size often all need to be block-size-aligned) and forfeits the kernel's often-quite-good general-purpose readahead/writeback heuristics, which the application must then reimplement itself if it wants comparable benefit.

## AIO (Linux Native Async I/O)

The `aio_read`/`aio_write` family (and the related `io_submit`/`io_getevents` Linux-specific interface) provided asynchronous disk I/O well before `io_uring` (§07/§10) existed -- but with real, long-standing limitations (effectively only worked well for `O_DIRECT` reads/writes on regular files, with awkward or missing support for many other cases, and a comparatively clunky completion-notification API). `io_uring` was designed specifically to be a general, efficient async I/O interface without AIO's carve-outs, and has largely superseded it for new systems-level code -- AIO is worth recognizing when reading older/existing codebases, not generally worth reaching for in new work.

## The Page Cache

Ordinary (non-`O_DIRECT`) file reads/writes on Linux go through the kernel's **page cache**: a read populates cache pages from disk (or serves directly from cache if already resident); a write updates cache pages and marks them dirty, with the kernel's **writeback** mechanism flushing dirty pages to disk asynchronously on its own schedule (or synchronously, if the application calls `fsync`/`fdatasync` to force durability at a specific point -- the exact primitive a write-ahead log, below, depends on for its durability guarantee). The page cache is why a second read of the same file is typically dramatically faster than the first, with no application-level caching code involved at all -- and why "how much free RAM does this machine have" is a misleading question on Linux, since a large fraction of "used" memory is often reclaimable page cache, not memory something would actually miss if reclaimed under pressure.

## B-Tree Indexes

A B-tree (specifically, the B+Tree variant nearly every real database index uses) is a **balanced, high-fanout** tree -- each node holds many keys (often hundreds, sized to fill one disk page/block) rather than the 1-2 a binary tree node holds, which directly minimizes the number of disk-page reads (handbook §37.1's cache-friendliness principle, applied at the disk-block granularity instead of the CPU-cache-line granularity) needed to locate any given key: a B+Tree with fanout 200 needs only ~4 levels to index a billion keys, versus ~30 levels for a binary tree. The **B+** specifically means only leaf nodes hold actual data (or data pointers); internal nodes hold only keys for routing -- and leaves are typically linked together in a sequential chain, making range scans (`WHERE key BETWEEN a AND b`) a simple leaf-to-leaf walk rather than repeated top-down tree traversals. B-trees update **in place** -- inserting/updating a key modifies the existing node directly (with occasional node splits when a node overflows) -- which makes them naturally good for read-heavy, update-in-place workloads, but means every write is, at the storage layer, a **random** I/O to wherever that key's leaf node happens to live on disk.

## LSM-Trees

The **Log-Structured Merge-tree** takes the opposite tradeoff: writes are never in-place. New writes go into an in-memory **memtable** (typically a sorted structure like a skip list or a balanced tree), and once the memtable reaches a size threshold, it's flushed to disk as an immutable, sorted **SSTable (Sorted String Table)** file -- a purely **sequential** disk write (handbook §37.1's sequential-access-is-fast principle, at the storage-device level), regardless of how randomly-distributed the actual keys being written are. Reads have to check the memtable *and* potentially multiple SSTables (newest first, since a key might have been updated/deleted in a more recent SSTable) -- a real **read amplification** cost LSM-trees accept in exchange for write-side sequential-I/O throughput. **Compaction** periodically merges multiple SSTables into fewer, larger ones, both bounding the number of files a read has to check and reclaiming space from overwritten/deleted keys -- **leveled compaction** (SSTables organized into levels of increasing size, each level compacted into the next, bounding read amplification more tightly at the cost of more total compaction I/O) and **size-tiered compaction** (merge similarly-sized SSTables together, less total compaction I/O but higher read amplification/space overhead) are the two dominant strategies, and real systems (RocksDB, Cassandra) commonly let you choose between them per workload. This write-optimized profile is exactly why LSM-trees dominate write-heavy systems (time-series databases, systems ingesting large write volumes) where B-trees' random-write cost would otherwise become the bottleneck.

## WAL (Write-Ahead Log)

Both B-tree and LSM-tree engines need a **write-ahead log** for crash durability: before a modification is applied to the "real" data structure (a B-tree page, or even before it lands in the memtable, depending on the design), it's first appended to a sequential log file and `fsync`'d -- so that after a crash, replaying the WAL from the last known-durable point reconstructs any in-memory state (the memtable, dirty B-tree pages not yet flushed) that existed right before the crash. The WAL append is sequential I/O (fast) even when the actual logical modification is random (a B-tree update to an arbitrary page) -- this is precisely why systems that already write sequentially (LSM memtables) still maintain a *separate* WAL rather than relying on the memtable's own durability: the memtable lives in RAM and is lost entirely on crash/power-loss without it, regardless of how the eventual on-disk SSTable format behaves.

## Checkpointing and Recovery

Replaying an unbounded WAL from the beginning of time would make crash recovery slower the longer the system has been running -- **checkpointing** periodically records "everything up through WAL position X is durably reflected in the actual data structure already," letting recovery start replay from the last checkpoint instead of from scratch, bounding recovery time to roughly "time since the last checkpoint" rather than "time since the database was created." (Handbook §16's database-internals material covers the full ARIES-style analysis/redo/undo recovery protocol built on top of this same WAL+checkpoint foundation.)

## NVMe and SSD Internals

Flash memory is organized into **pages** (the unit of read/write, commonly 4-16 KB) grouped into **blocks** (the unit of *erase*, commonly composed of hundreds of pages) -- and critically, a page **cannot be overwritten in place**; it must be erased (at the whole-block granularity) before it can be written again. The SSD's firmware -- the **FTL (Flash Translation Layer)** -- maps logical block addresses (what the OS/filesystem thinks it's reading/writing) onto physical flash locations, and handles **garbage collection** (relocating still-valid pages out of a block before erasing it to reclaim space from invalidated/overwritten pages) and **wear leveling** (spreading writes evenly across all physical blocks, since each flash cell tolerates only a limited number of erase cycles before wearing out). **Write amplification** is the resulting, real, measurable phenomenon where the *physical* bytes written to flash exceed the *logical* bytes the application asked to write -- a consequence of the erase-before-write constraint and GC's need to relocate valid data out of blocks being reclaimed -- and it's precisely why storage engines that understand this (writing sequentially in large chunks, as LSM-trees naturally do; avoiding small random overwrites, as B-trees inherently cannot fully avoid) tend to produce measurably better real-world SSD longevity and throughput than naive random-write patterns. NVMe (as opposed to older AHCI/SATA) is the modern host-controller interface designed around flash's actual parallelism (many independent, deep command queues, matching flash's ability to service many operations concurrently across its internal channels) rather than the single-queue model SATA inherited from spinning-disk-era assumptions -- a direct hardware-interface-level acknowledgment that flash's performance characteristics are fundamentally different from the rotating media the older interfaces were designed around.

## Key Takeaways

- B-trees and LSM-trees make opposite tradeoffs on the same axis: B-trees keep reads fast and pay a random-write cost; LSM-trees make all writes sequential and pay a read-amplification (and periodic compaction) cost.
- A WAL exists to make an otherwise-volatile or otherwise-random-write data structure crash-durable via one thing every storage engine can do cheaply: a sequential, `fsync`'d append.
- Flash's erase-before-write constraint is the root cause of write amplification, garbage collection, and wear leveling all at once -- they're three facets of the same underlying hardware limitation, not three unrelated SSD quirks.

## Interview Notes

- "Why do LSM-trees generally outperform B-trees on write-heavy workloads, and what do they give up for it?" -- LSM-trees turn all writes into sequential appends (memtable flush → SSTable), avoiding the random-I/O cost a B-tree's in-place updates inherently pay; the tradeoff is read amplification (checking multiple SSTables) and ongoing compaction overhead to bound that amplification over time.
- "Why does a database often disable the OS page cache (`O_DIRECT`) instead of relying on it?" -- to avoid double-buffering the same hot pages in both its own buffer pool and the kernel's page cache, and because the database typically has better information than the kernel's general-purpose eviction policy about which pages are actually hot and shouldn't be evicted.
