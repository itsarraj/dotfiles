# Kernel Programming: Linux Internals, Drivers, and Rust-for-Linux

Prerequisite: handbook §36 (OS concepts from userspace's perspective) and Part VI (namespaces/cgroups as a userspace consumer of kernel functionality). This file flips the vantage point to the kernel's own internals, and covers what writing kernel code in Rust actually looks like.

## Drivers and Interrupt Handlers

A device driver's core job is translating between the kernel's generic subsystem interfaces (block devices, network devices, character devices) and one specific piece of hardware's actual register/DMA/interrupt interface (§14's embedded material covers the identical mechanisms -- memory-mapped registers, interrupts, DMA -- just at the microcontroller scale rather than a full OS's device model). A Linux driver registers **interrupt handlers** (via `request_irq` and friends) that run in a restricted context similar in spirit to §36.4's userspace-signal-handler constraints, but stricter: kernel interrupt handlers commonly run with interrupts themselves disabled and cannot sleep/block at all, which is why real drivers split work into a fast **top half** (the actual interrupt handler -- acknowledge the hardware, capture minimal state, and get out quickly) and a deferred **bottom half** (a tasklet, softirq, or workqueue, scheduled to run shortly after, in a context that *can* sleep/block and do the heavier actual processing) -- a pattern directly analogous to how a userspace `signalfd`-based design (handbook §45.3) defers real work out of the async-signal-safety-constrained handler context into an ordinary event loop.

## The Kernel's Own Memory Allocator

The kernel needs memory allocators for its own internal use (long before any userspace process exists to call `malloc`, and serving very different constraints -- it can't use its own to-be-implemented paging/swapping machinery to allocate the structures paging/swapping themselves depend on). The **buddy allocator** manages physical memory in power-of-two-sized blocks, splitting a larger free block in two ("buddies") to satisfy a smaller request and merging buddies back together when both become free -- a genuinely different strategy than the free-list/size-class approach handbook §5.1's userspace allocator walkthrough described, chosen specifically because it makes finding and merging contiguous physical memory efficient (important for satisfying requests for physically-contiguous ranges, which some hardware/DMA operations require) at some internal-fragmentation cost. **`kmalloc`** (for smaller, arbitrary-sized kernel allocations) is commonly built on top of a **slab allocator** layered over the buddy allocator -- pre-allocating and reusing fixed-size "slabs" of memory for objects of a given kernel data-structure type (e.g., a dedicated slab cache just for `task_struct`s, the kernel's own per-process bookkeeping structure), avoiding both the fragmentation and per-allocation setup cost that generic variable-sized allocation would otherwise incur for the same, frequently-allocated-and-freed structure type.

## The Scheduler, from the Inside

Handbook §36.7 described the scheduler from a userspace-visible perspective (preemption via timer interrupt); internally, Linux's default scheduler (the **Completely Fair Scheduler**, CFS) tracks each runnable task's **virtual runtime** (roughly, CPU time consumed, weighted by the task's priority/nice value) and always picks the runnable task with the *least* virtual runtime to run next -- implemented via a red-black tree keyed on virtual runtime, so "find the task that's had the least CPU time so far" is an efficient tree-minimum lookup rather than a linear scan. This is the concrete mechanism behind cgroups' `cpu.max`/CFS-bandwidth enforcement (handbook §42) -- the same scheduler whose fairness policy governs ordinary process scheduling is what a cgroup's CPU controller throttles by capping how much virtual runtime a cgroup's tasks are collectively allowed to accumulate within a given period.

## VFS (Virtual File System)

The kernel's abstraction layer that lets `read`/`write`/`open` (handbook §36.3's syscalls) work identically regardless of which actual filesystem (ext4, XFS, btrfs, NFS, or even a synthetic filesystem like `/proc` or `/sys` that isn't backed by a real disk at all) a given path resolves into -- VFS defines generic **inode**, **dentry** (directory entry, caching path-to-inode lookups), and **file** object structures with function-pointer tables (exactly the hand-rolled-vtable pattern from handbook §14.3/§18.1's `struct file_operations` reference) that each concrete filesystem implements, so the rest of the kernel (and every userspace program) interacts with one uniform interface regardless of the underlying filesystem's actual on-disk format.

## The Networking Stack, Internally

An incoming packet is represented internally as an **`sk_buff`** (socket buffer) -- a structure carrying the packet data plus metadata that gets progressively updated as the packet moves up through the stack's layers (link layer → IP → TCP/UDP → the actual socket the application reads from), with headers being stripped/inspected at each layer without unnecessary copying of the underlying packet data itself (the `sk_buff`'s data pointers are adjusted layer by layer, rather than the payload being copied at every layer boundary) -- directly analogous to the zero-copy principle handbook §10's networking chapter described at the application level (`sendfile`/`splice`), applied here internally within the kernel's own packet-processing pipeline. This is also exactly the structure XDP (handbook §10's eBPF/XDP material) is specifically designed to intercept *before* -- an XDP program runs at the point a packet arrives from the NIC driver, before the kernel has even allocated the `sk_buff` for it, which is precisely why XDP can process packets so much more cheaply than anything operating further up this stack.

## Rust-for-Linux

The ongoing effort to allow **Rust code in the Linux kernel itself**, alongside the existing C codebase -- not a rewrite, but a way to write *new* drivers and kernel modules in Rust while the vast majority of the kernel remains C. The kernel exposes a curated, deliberately restricted set of its internal C APIs to Rust via hand-written (and `bindgen`-assisted, handbook §31.4/§13) FFI bindings, wrapped in safe(r) Rust abstractions where feasible -- the actual value proposition being exactly handbook §14.3/§35's Rust-vs-C safety argument, applied to kernel code specifically: a kernel bug (a use-after-free, a data race) tends to be *more* consequential than an equivalent userspace bug, since it can compromise the entire system rather than one process, which is precisely why kernel code is an especially high-value place to apply Rust's compile-time-checked ownership guarantees. Real constraints unique to this environment: kernel code is inherently `#![no_std]` (handbook §34/§14 -- there is no underlying OS providing `std`'s services, since the kernel *is* the OS), typically runs with **`panic = "abort"`** rather than unwind (handbook §17.1/§25 -- unwinding through arbitrary kernel call stacks, some of which may be holding locks or running with interrupts disabled, is far more fraught than in an ordinary userspace process), and allocation failure must be handled explicitly and gracefully everywhere (a kernel allocation failing is a routine, expected condition under memory pressure that code must handle correctly, not an exceptional case to `unwrap()`/panic on the way ordinary userspace code often reasonably does) -- Rust-for-Linux's fallible-allocation-aware APIs (`try_new`-style constructors instead of an infallible `new` that would abort on OOM) exist specifically to make that discipline the natural, ergonomic default rather than something a kernel-Rust author has to remember to opt into manually.

## Key Takeaways

- The top-half/bottom-half interrupt handler split in kernel drivers is the same "defer real work out of a heavily-restricted handler context" pattern userspace's `signalfd` approach uses, just enforced more strictly (kernel handlers genuinely cannot sleep).
- CFS's virtual-runtime-based scheduling (always run the task with the least accumulated weighted CPU time) is the actual mechanism cgroups' CPU limits are enforced through -- it's the same scheduler, constrained.
- Rust-for-Linux's value proposition is exactly the memory-safety argument from Part IV/§35, applied specifically to code where a bug's blast radius is the whole system rather than one process -- with kernel-specific constraints (no_std, abort-not-unwind, mandatory fallible allocation) shaping how idiomatic kernel Rust actually looks.

## Interview Notes

- "Why do Linux drivers split interrupt handling into a 'top half' and 'bottom half'?" -- the actual hardware interrupt handler runs in an extremely restricted context (often with interrupts disabled, unable to sleep) and must return quickly; heavier processing is deferred to a bottom half (tasklet/softirq/workqueue) that runs shortly after in a less restricted context that can safely do more work.
- "Why does kernel Rust code typically use `panic = \"abort\"` and explicit fallible allocation rather than the userspace-common `unwrap()`-on-OOM style?" -- unwinding through kernel call stacks (which may hold locks or run with interrupts disabled) is unsafe/impractical in many contexts, and an allocation failure under memory pressure is a routine condition the kernel must handle gracefully rather than treat as an exceptional, abort-worthy event.
